## 初始结论

Aurora 已有实用的本地／远程开发工作台和独立 AI 执行链，但距离完整 AI IDE，主要差距是：

1. **语言理解与开发闭环**：缺少语言服务器、诊断面板、语义补全／跳转／重构、调试器及任务／测试管理。
2. **编辑状态与 AI 的一致性**：缺少崩溃后的未保存正文恢复，以及从编辑缓冲、选区、诊断到 AI 编辑预览／接受的闭环。
3. **规模化状态管理**：会话全文加载／保存、快照扫描、文件监听和传输背压仍需分层优化。

本轮已修复可局部验证的性能与可靠性缺陷。大型能力缺口需分阶段实现，不能由补几个按钮替代协议、状态和恢复设计。

### 建议优先级

**P1：先建立文档与语言基础。**

- DocumentModel：统一 URI、版本、已保存版本、dirty、编辑缓冲、磁盘变更和撤销边界。
- 恢复日志：debounce 写入未保存文本，恢复时核对源文件版本，覆盖退出、崩溃、离线及磁盘满。
- LSP：先实现 initialize、didOpen/didChange/didSave/didClose、diagnostics、completion、hover、definition，再接 rename/codeAction/formatting/WorkspaceEdit。远程服务器进程由相应 agent 管理。
- 任务／问题面板：可取消、可重跑、可定位文件行列，保存执行配置与退出码。

**P2：再补 DAP、测试适配器、编码／大文件模式及跨文件替换。**

## 2. AI 功能与执行链

### 已有的有效基础

- Chat、Responses、Anthropic、ChatGPT 订阅路由；模型能力、思考配置及接收时冻结的输入快照。
- Build／Plan、补充／排队、审批、子代理、结构化问答、shell、读写／精确编辑／多文件补丁、检索和 Web 工具。
- 图片／PDF 作为不可变附件引用；逐工具检查点；重启不自动重放结果未知的副作用。
- 上下文估算、自动／手动压缩、历史恢复、重试及 Retry-After；已有懒加载 transcript 和隐藏视图流式绘制节流。
- OpenCode 兼容协议、`User-Agent`、`originator`、`x-opencode-client` 标识继续保留。

### 重要缺口

| 优先级 | 缺口 | 证据与建议 |
|---|---|---|
| P1 | AI 与未保存文档不共享事实源 | “附加当前文件”走远程文件读取；未见编辑缓冲版本、选区、LSP 诊断的统一上下文接口。必须区分磁盘版本与未保存版本，避免 AI 编辑与用户缓冲相互覆盖 |
| P1 | 缺少编辑器内联修改闭环 | 有工具 diff／审批，不等于针对当前缓冲的 inline edit、逐块接受／拒绝、多文件待审变更集、撤销合并 |
| P1 | 回退仍非完整事务 | 本轮修复路径越界、原子替换及运行互斥；仍可能覆盖 AI 修改后用户新写的内容，中途失败时可能已有部分文件恢复。需要“AI 修改后的预期版本”校验、整批回滚及文件变更与会话检查点的统一恢复日志 |
| P1 | 长历史与快照生命周期 | agent 初次初始化加载全部会话全文；压缩减少模型输入，并不删除原始历史。缺少摘要索引、按需加载、分页、快照 GC／容量预算 |
| P2 | 行内续写／下一编辑建议 | 未发现 AI ghost text、行内补全或 next-edit 实现；需复用文档版本与取消机制，并设置延迟、请求量和接受率预算 |
| P2 | 工程上下文获取较浅 | `discoverInstructions` 只读工作目录的首个 AGENTS.md／CLAUDE.md／.cursorrules；未见父级／子目录指令作用域、符号图或增量索引 |
| P2 | 通用扩展接口 | Exa 搜索使用 MCP 请求不代表有通用 MCP 管理；未见通用 MCP server 生命周期、工具发现、资源／提示管理或可安装技能系统 |
| P2 | 缺少自动质量闭环 | shell 能运行测试，但没有把任务、测试、lint、诊断及修改集关联到一次 AI 运行的结构化验证结果 |
| P2 | 评测与成本预算 | 现有协议／工具测试有价值，还需固定代码任务集、真实模型成功率、工具延迟、重试／压缩次数、输入输出成本及长任务预算 |

真实设备授权、账号资格和识图质量仍需要真实模型账号；本轮本地 SSE 夹具验证执行链与协议。

## 3. 本轮可靠性修复

### 已复现的高风险回退问题

`agent/internal/ai/snapshot.go:RestoreFiles` 原先按字符串检查路径后使用 `os.WriteFile`。如果工作区里的目录或最终文件被替换成符号链接，回退会写入链接指向的工作区外文件；测试在独立临时目录实际复现了越界改写。

现在使用 `os.OpenRoot` 约束所有写入、创建、删除、临时文件清理和重命名；最终文件通过原子替换恢复，复用工具提交锁，删除失败返回错误，非普通快照条目明确拒绝。三项实文件回归覆盖目录链接、最终文件链接、删除失败。

### 会话执行与落盘

- 回退先请求停止，确认 runner 已退出后才允许修改历史；异步取消不再被当作任务已经结束。
- 手动压缩／回退有会话独占状态；新输入与重叠维护不能穿插，停止可取消维护。
- 压缩和回退不再吞掉检查点写入错误；失败时保留原内存历史，不发成功事件。
- 保存会话移除 JSON 编码→解码→编码的重复克隆；仍通过 JSON tags 排除凭据和请求期媒体，空 messages 保持数组。
- 注入非法 RawMessage 的回归证明旧实现可能把序列化失败转成空会话并覆盖检查点；现在直接返回错误并保留原文件。此为故障防御测试，不声称正常 Chat 参数解析会产生该输入。
- AI subscriber 满队列时发全会话 `sync.required`，客户端重新同步；不再假定被丢弃的必定是 delta。

### 搜索

- 多 worker 在提交结果时重新核对共享上限，避免竞争导致返回条数超额。
- 取消、截断或遍历失败的文件列表不再污染后续快速打开缓存。
- 多目录快速打开严格遵守总条数上限，输入变化立即使旧结果失效，并核对当前连接。

### 客户端异步状态与 PDF

- 文件监听在连接切换、取消及关闭时使用代次与流身份验证；旧握手不会占住新连接，也不会接管新监听。
- Git 的仓库发现、状态、分支、历史、stash、tag 核对仓库／连接／请求代次；旧成功或旧失败都不能覆盖新仓库状态。
- AI 侧栏历史／搜索核对连接及请求代次；输入变化时立即失效旧搜索；历史行改为 builder 按需构建。
- PDF 读取共享最多 4 个在途块请求，范围读取边获取边填充输出缓冲；校验声明范围与实际包长，关闭期间迟到的流立即 reset。
- 客户端新增故障用例在修复前实际出现 **11 项失败**，包括旧 Git 结果串仓库、监听重连被旧握手阻塞、一次 PDF 读取同时开启 29 个请求、超长响应和快速打开结果超额；修复后定向回归通过。

## 4. 性能测量

同机 Windows amd64，Intel i7-1165G7，Go 1.26，`CGO_ENABLED=0`，每组 `-benchtime=500ms -count=3 -benchmem`，下表为三次中位数。原始记录见 `performance/20261116-audit-go-before.txt`、`performance/20261116-audit-go-after.txt`。

| 场景 | 修改前 | 修改后 | 每次分配前 → 后 |
|---|---:|---:|---:|
| 会话保存，100 条消息 | 7.944 ms | 4.541 ms | 3.138 MB → 0.647 MB |
| 会话保存，1000 条消息 | 43.289 ms | 15.308 ms | 31.888 MB → 6.924 MB |
| 快速打开，10 万路径，`file`，取前 100 | 128.687 ms | 6.002 ms | 12.970 MB → 0.0028 MB |
| 快速打开，30 万路径，`file`，取前 100 | 514.150 ms | 25.648 ms | 41.249 MB → 0.0028 MB |
| 快速打开，30 万路径，空查询 | 472.039 ms | 5.209 ms | 41.249 MB → 0.0028 MB |
| Windows 目录签名，5000 项 | 152.482 ms | 0.586 ms | 627.899 MB → 0.240 MB |

方法及边界：

- 会话基准调用实际 `persistSessionLocked`，包括临时文件、同步与重命名；每条消息含工具调用和约 4 KiB 输出。
- 排序使用确定性打乱的路径，堆只保留前 K 项，并一次规范化查询；测试对照全量排序，包含大小写、中文、空格、重复路径和不同上限。
- 目录签名用稳定 DirEntry 夹具隔离算法开销，不含 Windows 目录枚举／磁盘延迟；原算法逐次字符串拼接，现为流式 SHA-256。分配量包含夹具的 FileInfo 对象。
- MB 为十进制。数字代表热点本身，不代表整个 IDE 的打开速度、CPU 或内存降低相同比例。
- 原生 GUI 当前版本回归通过，结果见第 6 节；未将旧 Profile 数据计为本轮前后对照。

## 5. 全项目性能：继续优化的顺序

| 优先级 | 热点／边界 | 现状、建议及验收指标 |
|---|---|---|
| P1 | 会话全局锁 | 优化后仍在 `e.mu` 内完整编码并同步写盘；转为每会话锁＋单会话有序 writer，进一步采用增量 journal＋定期 checkpoint。测多会话并发时 p95 admission/get 延迟 |
| P1 | 影子 Git 快照 | 每个 Build 步骤前 Capture、工具后再 Capture；全局快照锁；每个 diff 文件再启动 Git；先完整缓冲输出再截断。改按工作区锁、跳过纯只读步骤、批量 diff、有界输出、容量／文件大小限制 |
| P1 | 下载背压 | `Transfers._runDownload` 的 `IOSink.add` 未等待磁盘写入；高速网络／慢盘可能积压；进度每块通知。改有界写队列／分批 flush，帧预算内合并进度；测 RSS 与终端 p95 延迟 |
| P1 | 传输结束／取消生命周期 | 打开流期间的取消、异常退出流清理、重试捕获旧 Link、已移除 Transfer 的 listener 生命周期仍需专门回归 |
| P2 | Windows 监听 | 本轮消除了签名构造的二次方复制，但仍每 800 ms 扫目录，最多 512 个目录、每目录前 5001 项；改 ReadDirectoryChangesW＋有界 fallback，暴露不完整监听状态 |
| P2 | 编辑器 dirty | re_editor 的 `.text` 会遍历行并组装全文，光标通知也进入 dirty 比较；应基于文档版本／保存点，严格覆盖 undo、IME、折叠、保存期间编辑 |
| P2 | Git diff | `text_diff.dart` 在 UI isolate 建最高约 400 万格 LCS 表；已有阈值降级，但仍应换有界 Myers／后台 isolate，测长文件切换帧时间 |
| P2 | Profile 保存 | 已有 500 ms 合并、原子加密写入、串行提交及轻量 getter；仍整份拷贝／编码／加密，布局与大代理订阅共存时需测 p95 保存阻塞，考虑分离非敏感视图状态 |
| P2 | 搜索取消 | 参数变化即失效 UI 结果只是第一步；需要可取消 operation handle，RST 贯通 agent context，快速输入时只保留有限在途请求 |
| P2 | 终端／监控／网络 | 终端保活、批量流优先级、4 MiB yamux 窗口、监控可见性轮询及 GPU 缓存已有；重点做慢读者、多流、慢磁盘、断连重连和 24 小时泄漏测试 |

监控已有 Windows 原生计数器、独立 system/GPU 快照、连接代次和隐藏暂停，不能再把“取消每次 PowerShell 采样”当成待实现优化。

另外，普通 `fs.write` 的 etag 检查与重命名之间仍有并发窗口，且不与 AI 工具共享提交事务；需要统一文件变更服务，覆盖两个客户端同时保存及 AI／用户同时修改。`fsSearch` 的大小判断在 `ReadFile` 之前，增长中的文件还需通过有界 reader 限制实际读取量。
