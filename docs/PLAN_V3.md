# Aurora v3 实施计划与目标

状态：设计（`REDESIGN_V3.md`，D-1 至 D-68）已由用户确认。本文是实施计划，按目标逐项完成，每个阶段的验收由用户确认。

## 环境

- Go 1.26.0：安装到 `<go-sdk>`，与 v2 的 `build.ps1` 路径一致。下载后必须与 go.dev 公布的 SHA-256 核对。
- WSL Ubuntu-24.04：Linux 构建与测试。它已运行 v2 的 agent（"Finnwe"），v3 测试不能直接覆盖它，见 G7.1。
- Docker：本机没有。tmux 构建（D-20）需要 Alpine 容器，见 G4.1。

## 约定（实施假设）

- Go 模块名 `aurora3`。v3 不引用 v2 的任何包路径。
- 代码从 v2 复制（决定 4），每个复制的文件记录来源（v2 提交 `f0d209c` 内的路径），复制后逐字节比较。
- 只读引用 v2。不在 v2 工作区里构建或改文件。已发生一次例外：用 `-mod=mod` 构建时改动了 v2 的 `go.mod`，已用 `git checkout` 还原，工作区恢复干净。之后在 v2 中只执行只读命令（`git show`、`git cat-file`、读取文件）。
- 提交信息用英文，文档用中文，与已有提交一致。

## 阶段与目标

### G0 准备

- G0.1 Go 1.26.0 可用。验收：`go version` 输出 `go1.26.0`，安装包哈希与官方一致。
- G0.2 v3 仓库有 `go.mod`、目录结构、agent 与 client 的入口。验收：Windows 与 Linux 上都能 `go build`。
- G0.3 tmux 构建锁与脚本复制到 `tools/tmux`。验收：与 v2 逐字节一致。
- G0.4 构建脚本：`linux/amd64`、`linux/arm64` 的 agent，Windows 客户端。验收：三个产物都能生成。

### G1 agent 内核

- G1.1 服务接口与注册表（D-40、D-44）。
- G1.2 `agent.json` 的 `services` 开关，缺省为开（D-41）。
- G1.3 `agent.info` 按服务上报，依赖缺失时标为不可用（D-42、D-43）。
- G1.4 固定在入口的操作：`agent.info`、`agent.health`、开关读写、p2p、令牌轮换（D-46、D-59）。
- G1.5 复制 `wire`（版本改为 3.0，D-65）、`update`（换为 v3 公钥，加撤回清单，D-67）、`netproxy`、`p2p`。
- 验收：单元测试覆盖开关、分发拒绝（D-44）、依赖缺失的错误信息。

### G2 agent 服务（D-45）

- G2.1 `terminal`：会话与终端流。关闭时保留已有会话（D-51、D-52）。
- G2.2 `files`：`fs.*`，含上传下载与批量计数（D-36）。
- G2.3 `git`：`git.*`。
- G2.4 `devtools`：`tools.*`、`dev.probe`、`lsp.start`、`dap.start`、`py.envs`。
- G2.5 `net`：`net.dial`、`net.ports`。
- G2.6 `monitor`：`sys.metrics`、`proc.list`、`gpu.info`、`log.tail`。
- G2.7 `systemd`：`svc.info`、`svc.action`，受 `service_actions` 白名单限制（D-28）。
- G2.8 `proxy`：按会话，创建时决定，默认关闭（D-47 至 D-50）。关闭时不启动监听，已有会话保留（D-53）。
- 验收：每个服务有开关测试；关闭后新操作被拒，已有会话不被结束（D-54）。

### G3 生命周期

- G3.1 安装四阶段：探测、准备校验、切换、确认。缺 systemd 或 systemd-run 即拒绝（D-15 至 D-17、D-35）。
- G3.2 升级切换与看门狗：只等批量传输结束，健康检查只看本地服务，失败版本记下（D-36、D-38、D-39）。
- G3.3 卸载：先列活动会话，默认保留配置，显式停止 `aurora-tmux-*`，彻底清除单独一步（D-31 至 D-37）。
- G3.4 登记挑战：ed25519 公钥挑战，签名绑定 TLS exporter（D-63）。
- 验收：在 WSL 测试实例上完整跑安装、升级、回滚、卸载，每一步有日志。

### G4 tmux

- G4.1 `amd64` 静态 tmux，按 D-20 在 Alpine 容器中构建，`bundle.lock` 校验。需要先在 WSL 中装 Docker 或改用等价的 Alpine 构建环境，并记录选择。
- G4.2 `arm64` 构建，并按 D-21 验证：真机或 QEMU 中 tmux 启动、attach、UTF-8 正常、agent 重启后会话存活。未通过不发布。
- 验收：amd64 通过；arm64 的结论写入文档，未通过则不进入发布产物。

### G5 客户端（界面重做，决定 3）

- G5.1 DPAPI 存储 SSH 凭据和直连参数（D-1、D-22），复用 `dpapi_windows.go` 的思路，代码重写。
- G5.2 SSH 连接与主机指纹确认，记入 known_hosts（D-2）。
- G5.3 安装向导：显示 G3.1 各阶段的进度与结果。
- G5.4 直连与重连：认证失败不重试，网络失败 3 次（D-24）；令牌被拒与指纹不符分开提示（D-62）。
- G5.5 服务开关界面，按 agent 上报的服务展示（D-30、D-42）。
- G5.6 界面技术选型：在本阶段开始前决定，选型理由写入 `REDESIGN_V3.md`。
- 验收：WSL 测试实例上走通"添加服务器、安装、连接、开关服务、卸载"。

### G6 VPS 登记（可选）

- G6.1 relay 只保留登记与会合，删除直连令牌分发和更新分发（D-9、D-63、D-64）。
- G6.2 不启用 VPS 时，G1 至 G5 的全部功能可用。
- 验收：启用 VPS 时代理与打洞可用；关闭 VPS 时无任何功能损失。

### G7 测试与发布

- G7.1 测试顺序：先在 WSL 的独立测试实例中验收（见下方说明），通过后才上 test-server（`203.0.113.10`）。test-server 当前运行 v2 agent，上测试前先备份其 `/etc/aurora` 与 `/var/lib/aurora`，并记录回滚步骤。
- G7.2 发布：第一个版本只生成产物和清单，不上传 GitHub Release。上传是对外且难撤回的动作，等用户确认。
- G7.3 v2 到 v3 的迁移设计在 G7.1 通过后开始（D-58）。

WSL 测试实例说明：WSL 里的 `Ubuntu-24.04` 运行着 v2 agent，直接安装 v3 会冲突（同一路径 `/usr/local/bin/aurora-agent`）。计划是另建一个 WSL 发行版，专门用于 v3 测试。这需要下载发行版，属于环境变更，先在 G0 中确认可行性。

## 停止条件

以下情况停下来报告，不自行继续：

- 需要对外发布、上传、删除或覆盖任何 v2 文件或 v2 运行中的服务器状态。
- 某个验收条件失败，且原因不明。不跳过失败的验收。
- 设计与代码现实冲突，需要改变已确认的决定。这种情况写成新的决定编号，并等待用户确认后再实施。
