# Aurora 设计

本文是 Aurora（v3）的唯一设计文档，汇总至 D-114。旧的讨论记录在 `docs/history/`，只作追溯，以本文为准；各决定中的版本范围保留为历史说明。

## 1. 目标

Aurora 是以标签页为工作单元的本地与远程开发工作台，同时提供比 SSH 更强的远程服务器管理能力。

### 核心理念：标签页优先，布局服务于任务

文件、终端、AI 会话、差异和工具视图都是可组合的工作单元，而不是被固定在某个功能页面里。用户决定它们在哪里、以什么顺序和多大尺寸出现；功能入口负责打开任务，编辑组负责组织任务。

- **状态比位置重要**：移动、拆分、合并、换排布、缩放窗口不等于关闭或重新打开任务；同一标签只持有一份编辑缓冲、撤销历史或终端流。
- **布局可预测**：拖放目标明确、分隔条可发现且可复位，鼠标操作有菜单/键盘替代；窄屏只聚焦显示，不销毁宽屏布局。
- **尊重已有工作**：固定标签在批量关闭时受保护，未保存修改仍需确认；布局记忆只保存路径引用和几何，不把未保存内容、凭据或任务进程伪装成可恢复状态。
- **用验收而不是口号评价体验**：“比 VS Code 更好”是持续目标，先验证操作成本、可发现性、状态连续性和错误恢复，不把尚未做过的真实用户对比说成结论。

- **服务器端**：只装一个 `aurora3-agent`（Go）。它是入口，负责身份、连接、分发。终端、文件、git、代理、监控等都是挂在入口上的服务，可以单独启停。
- **客户端**：Flutter/Dart 编写，一套代码面向 Windows、Linux、macOS、Android、iOS（D-70）。负责安装 agent、建立连接、提供界面。
- **VPS**：可选，只提供代理网络和打洞，不承担任何凭据。

v2（标签 `archive/v2-final`，提交 `f0d209c`）已封存，只读参考，不修改，不在其目录里构建（D-75）。

## 2. 使用流程

1. 用户安装客户端。
2. 用户输入服务器的 SSH 地址和账号。SSH 凭据可加密保存在本机（D-1、D-72）。
3. 客户端通过 SSH 登录，核对主机指纹（D-2），推送内置的 agent 并校验签名（D-3），按四阶段安装（D-15 至 D-17）。
4. agent 首次启动时生成身份：证书和直连令牌。
5. 客户端经同一条 SSH 通道读取直连参数（证书指纹、令牌、地址、端口），然后断开 SSH（D-4）。
6. 之后日常使用只走直连（TCP + TLS + yamux），不依赖 SSH。
7. （可选）启用 VPS：agent 登记到 VPS，解锁代理网络和打洞。

凭据流向：SSH 凭据只在"用户 → 客户端 → 服务器"之间流动；直连令牌只在"服务器 → 客户端"之间流动。两者都不经过 VPS。

## 3. 仓库结构（D-74）

```
Aurora 3 源码仓库/
  agent/          Go：aurora3-agent（模块 aurora3）、tmux 构建工具
  app/            Flutter：客户端（多端）
  docs/           本文、实施计划、旧讨论记录
```

- 客户端与 agent 在同一仓库，协议两端一起改，共用一个版本号。
- 客户端安装包内置 agent（D-3、D-14），构建时从 `agent/` 取产物。
- 本仓库由 早期的 `aurora-v3` 仓库 克隆而来，保留其全部提交历史。`aurora-v3` 之后不再使用，但不删除。

## 4. 与 v2 隔离（D-71、D-75）

v3 的所有名字都与 v2 不同，两者可以装在同一台机器上互不影响：

| 项目 | v2 | v3 |
|---|---|---|
| 二进制 | `/usr/local/bin/aurora-agent` | `/usr/local/bin/aurora3-agent` |
| systemd 单元 | `aurora-agent.service` | `aurora3-agent.service` |
| 配置 | `/etc/aurora/agent.json` | `/etc/aurora3/agent.json` |
| 状态 | `/var/lib/aurora` | `/var/lib/aurora3` |
| 开发工具 | `/usr/local/lib/aurora/tools` | `/usr/local/lib/aurora3/tools` |
| tmux 单元 | `aurora-tmux-*` | `aurora3-tmux-*` |
| 直连端口 | 7700（WSL 上的 v2 改成了 7710） | 17710（D-76） |
| 客户端数据（Windows） | `%LOCALAPPDATA%\Aurora` | `%LOCALAPPDATA%\Aurora3` |
| 协议版本 | 2.0 | 3.0 |
| 发布密钥 | `dbca22993317d40b` | `87828dfb18459372` |

规则：

- v3 的任何清理、扫描、卸载只匹配 `aurora3` 前缀，不能匹配 `aurora-` 或 `aurora*`。v2 的 `aurora-tmux-*` 不是 `aurora3-tmux-*` 的前缀，反之亦然。
- 测试和部署不触碰 v2 的文件、进程、单元和端口。在跑着 v2 的机器上（WSL Ubuntu-24.04、203.0.113.10）测试 v3 前，先确认上表中 v3 的名字都未被占用。
- 不在 v2 的目录里执行写操作或构建，只读（`git show`、`git cat-file`、读文件）。
- 迁移（D-55）改为并行安装：先装 v3 并确认可用，再由用户单独决定卸载 v2。

## 5. 决定一览

### 5.1 安装与身份

| 编号 | 问题 | 决定 |
|---|---|---|
| D-1 | SSH 凭据是否保存 | 加密保存在本机，机制见 D-72 |
| D-2 | 首次连接的主机指纹 | 首次 SSH 时显示服务器指纹，用户确认后记入客户端自己的 known_hosts |
| D-3 | agent 二进制的来源 | 内置于客户端安装包，并校验签名；安装不依赖 VPS |
| D-4 | 直连参数如何交给客户端 | 安装完成后，经同一条 SSH 通道读取，然后断开 SSH |
| D-5 | 无 SSH 的服务器 | 第一版只支持 SSH，其它方式作为后续项 |
| D-6 | sudo | 支持 sudo；sudo 密码也可以同样加密保存 |
| D-14 | 内置架构 | `linux/amd64` 和 `linux/arm64`。其它架构安装时明确报"不支持" |
| D-15 | 安装的原子性 | 要么整体成功，要么完全回滚到安装前，不留中间状态 |
| D-16 | "可恢复的原子"的定义 | 切换阶段是毫秒级的本地 rename；任何失败都回滚到切换前的完整状态 |
| D-17 | 残留安装的清理 | 确认失败后立即清理。仅当回滚成功才删除目录；回滚失败时保留回滚目录并向用户显式报告 |
| D-18 | 切换时的断线 | 接受一次短暂断线：终端会话在 tmux 中不丢，客户端自动重连 |
| D-19 | tmux 来源 | 使用 agent 内置的静态 tmux，不依赖系统 tmux |
| D-20 | tmux 构建流程 | 源码按 `sources.lock` 固定并校验，在 Alpine 容器中构建静态 tmux，产物哈希写入 `bundle.lock`，构建时不匹配则拒绝 |
| D-21 | arm64 tmux 的发布条件 | 必须在真实 arm64 或 QEMU 上验证：启动、建立会话、attach 后输入输出正常、UTF-8 中文正确、agent 重启后会话存活。未验证不发布 |

安装四阶段（D-15 至 D-17、D-35）：

1. **探测**（不改任何东西）：架构、发行版、`systemd` 与 `systemd-run`（缺一即拒绝）、已有 v3 的版本。已有版本不低于内置版本时不覆盖（D-12）。同时检查 v2 是否存在，只用于提示，不改动它。
2. **准备与校验**（只写 `/var/lib/aurora3/install-<随机>/`）：放入新二进制、配置、单元；校验 SHA-256，配置能被解析，单元通过 `systemd-analyze verify`。失败则删除临时目录。
3. **切换**（唯一提交点）：保存当前状态到回滚目录，用 rename 换到正式路径，重启服务。
4. **确认**：服务在监听，证书可用。成功则删除回滚目录与临时目录；失败则回滚并再确认。

### 5.2 直连与凭据

| 编号 | 问题 | 决定 |
|---|---|---|
| D-22 | 直连参数本地保存 | 证书指纹与令牌加密保存在本机，与 SSH 凭据同一机制（D-72），按服务器分别存放 |
| D-23 | 令牌轮换的路径 | 走已建立的直连，不经过 SSH。新令牌生成后，旧令牌立即失效 |
| D-24 | 参数失效的处理 | 认证失败不重试，直接提示。网络失败最多重试 3 次（约 2、5、10 秒），仍失败才提示。不静默反复重试 |
| D-59 | 令牌轮换的触发 | 用户手动触发，不做定期自动轮换 |
| D-60 | 令牌轮换的流程 | agent 先原子写入 `agent.json`，写入失败则旧令牌保持有效；成功后在同一响应返回新令牌，旧令牌立即失效。响应丢失时客户端按 D-24 提示重新配对 |
| D-61 | 证书 | 不做主动轮换，只在证书丢失或重装时变化。私钥只在服务器上（0600，属 root）。有效期 30 年，客户端按指纹信任 |
| D-62 | 令牌被拒与指纹不符 | 分开报告。令牌被拒：提示重新配对。指纹不符：提示服务器身份已变化，不自动接受新指纹，不重试；用户确认后经 SSH 重新读取参数，SSH 主机指纹仍按 D-2 核对 |
| D-72 | 多端的凭据存储（修正 D-1、D-22 的实现） | 使用各平台的系统密钥库：Windows 用 DPAPI（当前用户），Android 用 Keystore，macOS/iOS 用 Keychain，Linux 用 libsecret。数据绑定本机，换设备需重新配对。不使用主密码。系统密钥库不可用时（例如 Linux 没有密钥服务）拒绝保存，并提示用户，不退回明文 |

### 5.3 传输（D-73）

客户端第一版只用 TCP 直连，不实现 QUIC，因此第一版客户端没有打洞（打洞建立在 QUIC 之上）。agent 端的 QUIC 与 p2p 代码保留，暂不启用。

协议栈（客户端到 agent）：

1. **TCP**：开启 `TCP_NODELAY`。
2. **TLS 1.3**：不校验 CA 与主机名，改为比较证书 DER 的 SHA-256（小写十六进制）与保存的指纹，不一致即断开（`wire.PinnedTLS`）。客户端的 TLS 由随 App 编译的 BoringSSL 完成（D-77，`app/packages/aurora_tls`）。
3. **Hello**：一个 `J` 帧，`{"role":"client","token":…,"version":"3.0","client":…}`；agent 回 `HelloReply`。握手限时 15 秒。主版本不同即拒绝（D-65）。
4. **yamux**：hashicorp/yamux v0.1.1 协议，客户端用奇数流号。参数与 `wire.MuxConfig` 一致：流窗口上限 4 MiB，keepalive 15 秒，写超时 30 秒，打开流超时 20 秒。
5. **请求**：每个操作开一个流，先发 `J` 帧 `Request{op,args}`。帧格式：4 字节大端长度（含类型字节）、1 字节类型（`J` JSON、`D` 数据、`E` 结束）、负载，单帧不超过 1 MiB。

性能要求（用户要求"把 TCP 性能优化好"）：

- 流窗口：每个流的接收窗口按 4 MiB 宣告，与 agent 一致，单流吞吐不受 256 KiB 初始窗口限制。
- 写合并：同一轮事件里待发的多个 yamux 帧合并成一次 socket 写，减少 TLS 记录数与系统调用。
- 不阻塞：读循环只解析帧并分发，数据拷贝不在读循环里等待上层消费。
- 服务器端沿用 v2 的 Linux TCP 调优：`TCP_NODELAY`、`TCP_NOTSENT_LOWAT=128 KiB`、`TCP_THIN_LINEAR_TIMEOUTS`。
- 交互优先：终端等交互流的帧不排在大文件传输后面（发送队列按流区分，交互流先发）。
- 验收：基准测试（1 个大流与多个并发流的吞吐、空载往返延迟、大传输进行中终端帧的延迟）在 WSL 上对 Go agent 运行，结果写入实施计划，并与 Go 客户端（hashicorp/yamux）的同项结果对比。

### 5.4 agent 内核与服务

| 编号 | 问题 | 决定 |
|---|---|---|
| D-8 | agent 的定位 | 入口只做身份、连接、分发；其余能力都是服务，可独立启停 |
| D-9 | 服务的默认启用 | 默认开启，用户可关闭 |
| D-25 | 安全前提 | 服务开关是功能选择，不是安全边界。agent 以 root 运行，持有直连令牌的人能取得 root 权限。D-72 的保护按这个级别要求 |
| D-26 | 服务开关的途径 | 经直连完成，每次变更写审计日志 |
| D-27 | 未内置的服务 | 客户端不能让 agent 启用未内置的服务 |
| D-28 | `service_actions` | systemd 启停的白名单，修改方式与服务开关相同 |
| D-29 | 插件 | 内核与插件的划分只为开发方便。服务随 agent 编译、随客户端分发。不做运行时加载外部插件 |
| D-30 | 功能由谁决定 | agent 上报它实际提供的能力，客户端只显示上报的能力 |
| D-40 | 服务的注册 | 服务是编译期固定的列表，经统一接口注册。服务之间不调用对方的内部函数；共享部分（路径规则、审计、会话）放在内核。跨服务的需要通过中性接口满足（如 `files.RepoRunner`） |
| D-41 | 开关的存放 | `agent.json` 的 `services`，按服务名记布尔值，缺省为开 |
| D-42 | 能力上报 | `agent.info` 按服务上报：名称、是否启用、是否可用、不可用原因、操作列表 |
| D-43 | 依赖缺失 | 服务标为不可用并说明缺什么；调用时返回明确错误；其它服务不受影响 |
| D-44 | 开关的强制执行 | 服务关闭后，其操作在分发层直接拒绝 |
| D-45 | 服务清单（8 个） | terminal；files（`fs.*`）；git（`git.*`）；devtools（`tools.*`、`dev.probe`、`lsp.start`、`dap.start`、`py.envs`）；net（`net.dial`、`net.ports`）；monitor（`sys.metrics`、`proc.list`、`gpu.info`、`log.tail`）；systemd（`svc.info`、`svc.action`）；proxy（控制会话代理环境） |
| D-46 | 固定在入口的操作 | `agent.info`、`agent.health`、服务开关的读写、p2p、令牌轮换。不能关闭 |
| D-51 | 关闭 terminal | 只禁止新建和连接；已有 tmux 会话继续运行；已连接的窗口被断开并说明原因 |
| D-52 | 关闭 terminal 后的清理 | `session.kill` 仍允许 |
| D-54 | 关闭服务的总原则 | 阻止新的操作，不强制结束已有工作 |

### 5.5.1 代理出口与订阅（D-83 至 D-90，2026-11-08）

Aurora 不修改任何代理服务器（D-83）。受控服务器（装 agent，SSH 添加）和代理出口（只被拨号，不装任何东西）是两种条目，凭据互不相通；同一台机器可以同时是两者，但在客户端里是两个条目。出口的来源是：一份机场的 Clash 订阅，一个分享链接，或手填的节点。

| 编号 | 问题 | 决定 |
|---|---|---|
| D-83 | 代理出口与受控服务器 | 两种条目，凭据分开。Aurora 不通过 SSH 在代理服务器上安装或修改任何程序。用户自己的 VPS 当作一个普通节点使用 |
| D-84 | 订阅在哪里拉取和解析 | 在客户端。订阅 URL 含节点凭据，按 D-72 加密保存在本机，不交给服务器。客户端每次连上受控服务器时重新拉取，已选节点的参数变了就推送一次。agent 只保存被选中的那一个节点，不保存订阅。节点的延迟测试由 agent 做（从受控服务器拨向节点），客户端本机到节点的延迟对国内服务器没有参考意义。agent 的代理延迟与客户端无关：数据只走 终端或 git → agent 本机监听 → 节点 |
| D-85 | 订阅格式 | 第一阶段优先 Clash YAML 的 `proxies:` 段，其次分享链接列表（可整体 base64）。不使用任何第三方订阅转换服务（会泄露节点凭据）。客户端用 `package:yaml`（MIT）解析 YAML，其余自写 |
| D-86 | 第一阶段的协议 | Hysteria2、VLESS、VMess，加 agent 已有的 Trojan。Shadowsocks 随后。每个协议在 agent 里是 `netproxy` 下的一个拨号器，对外同一个接口（给定目标，返回字节流）。agent 暂时拨不了的协议（TUIC、AnyTLS、Reality 等），客户端在列表里灰显并写明原因，不隐藏 |
| D-87 | VLESS 与 VMess 的实现 | 自写拨号器，不引入 Xray-core、v2ray-core 或 sing 系库。协议规范公开且简单：VLESS 是一个请求头，VMess 是 AEAD 认证头加 AES-128-GCM 或 ChaCha20-Poly1305 分块（`crypto/*` 与 `golang.org/x/crypto`，BSD）。传输层支持 tcp、tcp+TLS、WebSocket（`github.com/coder/websocket`，ISC，agent 已有）；gRPC、HTTP/2、XHTTP、Reality 第一阶段不做 |

| D-35 | tmux 与 agent | tmux 服务器运行在独立的 `aurora3-tmux-*` 单元中，agent 重启或升级不结束终端会话 |
| D-36 | 升级时的等待 | 只等批量传输（`fs.upload`、`fs.download`）结束，再保持 30 秒安静窗口。超时 15 分钟则不切换 |
| D-37 | 卸载与 tmux | 卸载时显式停止 `aurora3-tmux-*` 单元 |
| D-38 | 升级后的健康检查 | 本地服务就绪即可，不要求直连或 VPS |
| D-39 | 失败版本 | 回滚后记下失败版本，不再推送同一版本 |
| D-67 | 版本撤回 | 签名的撤回清单（`revoked`、`min_ok`），随客户端分发。服务器当前版本被撤回时，只推送未被撤回且不低于 `min_ok` 的内置版本 |
| D-68 | 发布私钥的备份 | 暂不做离线备份，接受单点风险。首个正式发布前重新评估 |

## 6. 新增决定（本次汇总）

| 编号 | 决定 |
|---|---|
| D-70 | 客户端全部用 Flutter/Dart 编写，面向多端，不做 Web。Go 只在服务器端 |
| D-71 | v3 使用独立的名字、路径、端口（见第 4 节），与 v2 共存。修正 D-55、D-56 |
| D-72 | 多端凭据存储使用系统密钥库（见 5.2） |
| D-73 | 第一版客户端只用 TCP 直连，不做 QUIC 与打洞；yamux 用 Dart 自行实现，并对 Go agent 测试；TCP 性能按 5.3 优化 |
| D-74 | 新仓库 `aurora`，客户端与 agent 合一（见第 3 节） |
| D-75 | 测试和部署不影响封存的 v2（见第 4 节） |
| D-76 | v3 默认直连端口为 17710（修正 D-71 中的 7710）。原因：WSL 上的 v2 配置为 `127.0.0.1:7710`。17710 在 WSL 和 203.0.113.10 上都空闲，且不在两台机器的临时端口范围内。新机器安装前仍在探测阶段检查端口是否被占用 |
| D-77 | 客户端的 TLS 不用 Dart 自带的 `SecureSocket`，改用随 App 编译的 BoringSSL（0.20261020.0，Apache-2.0），由 Dart 构建钩子为每个平台编译，不修改 Flutter 引擎。TCP 仍用 Dart 的普通 Socket，密文与明文经 FFI 在 Dart 与 BoringSSL 之间传递，不经过 IO 线程。原因：`SecureSocket` 固定 8 KiB 缓冲并在 IO 线程上加解密，本机只有 46–72 MB/s（dart-lang/sdk#64115，上游的修复在 2026-09 被拒绝）；Mbed TLS 4.1 的 AES-GCM 只有约 300 MB/s。Windows x64 构建需要 NASM 3.02（构建工具，不进安装包） |
| D-78 | 客户端的内核与功能（对应 D-8、D-40） | 客户端分内核和功能两层。内核（`app/lib/kernel`）管连接、每台服务器的工作区、编辑区标签页、布局、命令面板；功能（`app/lib/features`）各自是 agent 一个服务的客户端，声明自己要的服务和操作（`Feature.service`、`Feature.ops`）。功能列表在编译期固定，与 agent 的服务列表一致。功能之间不互相调用，共享的东西（标签页、提示、连接）经内核的 `Workspace`。agent 上报的服务状态决定一个功能怎样显示：读取中、可用、已关闭（带“打开这个服务”按钮）、缺程序不可用、agent 版本较旧（缺操作）、agent 没有该服务；客户端不自行猜测 |
| D-79 | 界面风格与输入方式 | 向 IDE 对齐：活动栏、侧栏、编辑区标签页、状态栏、命令面板（Ctrl+Shift+P），扁平、紧凑、严肃，深浅两套配色，颜色集中在 `ThemeExtension Ide`。三种宽度：≥900 px 全部显示；600–900 px 侧栏默认收起，需要时才浮出；<600 px 一次只显示一栏，底部是功能栏。鼠标与触控由最后一次输入决定，不由设备决定：鼠标行高 28 px，触控 44 px；每个菜单同时支持右键和长按；触控下终端多一排 Esc、Tab、Ctrl、方向键 |
| D-80 | 文件编辑的安全 | 在线编辑只打开 UTF-8 文本且不超过 512 KB 的文件；其它编码和二进制不当文本打开，以免保存时破坏原字节。保存带 `if_match`（文件的 etag），文件在打开后被别的程序改过则拒绝保存，由用户选择取消、放弃自己的修改重新载入、或明确覆盖。上传遇到服务器上的同名文件先问（替换、跳过、全部替换）。传输可取消：取消的下载删除临时文件，取消的上传不会替换原文件（agent 先写临时名，完整后才改名） |
| D-81 | systemd 授权名单可由客户端修改（补充 D-28） | `service_actions` 可经直连用入口操作 `agent.actions` 读取和修改，与服务开关一样：校验单元名和动作（`paths.CheckActions`，只允许 start、stop、restart）、保存到 `agent.json`、写审计日志；保存失败则不改。`systemd` 服务每次调用时读当前名单，所以修改立即生效。客户端对未授权的单元执行动作前，先请用户确认授权。入口操作不能被关闭（D-46） |
| D-82 | 端口转发（`net` 服务，D-45） | `net.ports` 列出服务器上监听的 TCP 端口，同一端口有多个监听时固定选对外最可达的一个；`net.dial` 连到服务器上的 host:port 并双向转发字节。客户端在本机 127.0.0.1 上为每个转发开一个监听（不绑其它地址），每个连接对应一个 `net.dial` 流，走批量优先级，不挤占终端按键。转发列表按服务器保存在加密的本机配置里，服务器连上时重新打开；本机端口优先用与服务器相同的号，被占用就换一个 |

| D-83 至 D-94 | 代理出口、订阅、协议、证书校验、节点身份、会话的代理变量（见 5.5.1） |
