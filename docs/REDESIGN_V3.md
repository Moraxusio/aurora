# Aurora 重新设计（v3）：草案

状态：草案，待逐项讨论。讨论定稿前不开工。

本文记录这次重新设计的目标、已确定的决定、待讨论的问题。"现状"部分都标注了代码位置，便于核对。

## 1. 目标

Aurora 的目的是提供比 SSH 更强的远程管理能力。服务器上只需要装一个 `aurora-agent`，它是一个**入口**，类似 SSH 的服务端：负责身份、连接、分发。终端、文件、代理、监控、开发工具等都是挂在入口上的**服务**，按需启用。

客户端（Windows 上的 Aurora）负责安装 agent、建立连接、提供界面和编辑器。

VPS 不是刚需。它是可选的增强，只提供两项能力：代理网络和打洞。它不承担凭据的任何角色。

## 2. 目标使用流程

1. 用户下载客户端。
2. 用户输入服务器的 SSH 地址和账号（SSH 凭据可加密保存在本地）。
3. 客户端通过 SSH 登录服务器，安装 agent，建立 systemd 服务并启动。
4. agent 首次启动时生成自己的身份（id、证书、直连令牌）。
5. 客户端通过同一条 SSH 通道读取 agent 的直连参数（证书指纹、令牌、地址）。
6. 客户端直接建立直连，之后日常使用不再依赖 SSH。
7. （可选）用户配置 VPS：agent 登记到 VPS，解锁代理网络和打洞。

凭据流向：SSH 凭据只在"用户 → 客户端 → 服务器"之间流动；直连令牌只在"服务器 → 客户端"之间流动。两者都不经过 VPS。

| D-34 | 卸载的分阶段与失败处理（Q3） | 卸载分阶段执行。任一步失败时报告已完成的步骤和当前状态，不自动回滚，因为卸载的目标本来就是删除 |
| D-35 | tmux 会话与 agent 的关系（Q3） | tmux 服务器运行在独立的 `aurora-tmux-*` systemd 单元中，不在 agent 的控制组内。agent 重启或升级切换不结束终端会话。依据：v2 `sessions.go:208-225`，`install.go` 的 `KillMode=mixed` |

| D-39 | 失败版本的处理（Q3） | 升级失败并回滚后，记下失败的版本。客户端不再推送同一版本，直到发布更新的版本 |

## 4. 现状（代码核对）

以下都是现在代码的实际情况，重新设计时要替换或保留的部分。

### 4.1 agent 的入口与服务
- 入口：直连 TLS（TCP）和 QUIC（UDP）两条链路，`internal/agent/server.go`。
- 认证：令牌加证书指纹（pin）。
- 中继登记：`relayLoop` 主动连 VPS，`server.go:249`。
- 服务：操作表集中在 `internal/agent/ops.go`，约 66 个操作，覆盖终端、文件、git、开发工具、端口、监控等。
- 耦合：`Server` 结构体直接持有代理、会话、监听等字段，入口和服务没有分开。
- 代理：agent 启动时无条件拉起会话代理（`server.go:236`）。按 D-9，它要改为可选、默认开启。

### 4.2 agent 的安装与身份
- 安装入口：`internal/agent/install.go`，写 systemd 单元 `/etc/systemd/system/aurora-agent.service`，配置 `/etc/aurora/agent.json`，状态目录 `/var/lib/aurora`。
- 身份：安装时生成 `Token`（`install.go:188`）；直连证书在 `/var/lib/aurora/agent.crt`、`agent.key`。
- 加入码：安装时若无参数，使用构建时烘焙进二进制的加入码（`BakedJoinCode()`，`install.go:217`）。**这是要消除的部分**，按 D-3/D-7，安装不依赖烘焙凭据，中继加入码只在启用 VPS 时才需要。

### 4.3 客户端
- 配置存储：`profile.dat`，经 `Sealer` 接口封装，Windows 下用 DPAPI（`internal/client/dpapi_windows.go`）。
- SSH：客户端没有 SSH 实现。`golang.org/x/crypto` 在依赖中，但标记为 indirect，项目未直接使用。
- 中继凭据：客户端当前通过 VPS 获得服务器的直连参数，其中包含直连令牌（`wire.DirectInfo.Token`，`internal/wire/messages.go:58`）。**这要改为：直连令牌不经过 VPS。**

### 4.4 VPS（relay）
- 职责现状：服务器目录、打洞信令（候选地址交换）、直连参数分发（含令牌）、更新分发（签名通道）。
- 数据不经过 VPS：非打洞请求被拒绝（`internal/relay/relay.go:677` 之后）。
- 凭据风险：VPS 持有每台 agent 的直连令牌（`docs/CLOUD_UPDATE.md:151`，决策 D2）。**这要改为：VPS 不持有任何直连凭据。**
- 打洞：候选地址由外部交换，打洞本身只负责发包和接收（`internal/p2p/p2p.go`）；STUN 用于取得 NAT 映射（`internal/p2p/stun.go`）。

## 5. 待讨论的问题

以下是需要和你逐项确定的部分。每一项我都给了建议，但不代表已定。

### Q1. 客户端如何内置 agent（已决定：D-14）
- 客户端内置 `linux/amd64` 与 `linux/arm64` 两种 agent，约 24 MB 的 agent 内容。
- 安装前先经 SSH 执行 `uname -m` 识别架构，选用对应的 agent。
- 其它架构（armv7、386、非 Linux）安装时明确报"不支持"。

### Q2. 安装的具体步骤与回滚（已决定：D-15 至 D-18）
安装分四个阶段，只有第三阶段会改动正式路径：

1. **探测**（不改任何东西）：架构、发行版、systemd 与 systemd-run 是否存在（缺一即拒绝）、已有安装的版本。已有版本不低于内置版本时不覆盖（D-12）。
2. **准备与校验**（只写临时目录 `/var/lib/aurora/install-<随机>/`）：放入新二进制、新配置、新单元；校验二进制 SHA-256 与内置清单一致，配置能被 agent 解析，单元通过 `systemd-analyze verify`。失败则删除临时目录。
3. **切换**（唯一的提交点）：把当前完整状态保存到回滚目录，再用 rename 逐个换到正式路径，最后重启服务。
4. **确认**：服务在监听，证书可用。成功则删除回滚目录与临时目录；失败则用回滚目录恢复并重启，再确认。

回滚规则（D-17）：回滚成功才删除目录；回滚失败时保留回滚目录，向用户显式报告其路径，不静默残留。

安装不依赖系统 tmux，使用内置的（D-19）。探测阶段另检查 `systemd-run`，缺失则拒绝安装（D-35）。

### Q3. 升级与卸载（已决定：D-31 至 D-39）

卸载：
- 由客户端经 SSH 执行。
- 先列出活动的 tmux 会话，有会话时需用户确认（D-31）。
- 默认卸载停服务、结束 `aurora-tmux-*` 单元、删二进制和单元，保留配置与状态（D-32、D-37）。
- "彻底清除"是单独一步，删除配置、证书、令牌、状态目录和开发工具（D-33）。
- 分阶段执行，失败时报告状态，不自动回滚（D-34）。

升级：
- 由客户端在连接时按 D-11、D-12 推送，agent 不从外部拉取更新。
- 切换只等待批量传输（`fs.upload`、`fs.download`）结束，不等待终端会话（D-36）。
- 切换的断线沿用 D-18；tmux 会话不丢（D-35）。
- 切换后的健康检查只看本地服务就绪（D-38）。
- 失败的版本记下后不再推送（D-39）。

### Q4. 直连参数的读取与更换（已决定：D-22 至 D-24）
- 参数读取一次后保存在本地（加密，D-22）。令牌轮换走直连，不经 SSH（D-23）。
- 待定：令牌轮换由谁触发（用户手动，还是 agent 定期轮换）。证书更换方式未讨论。

### Q5. VPS 作为可选项的接入方式（已决定：方案 b）
- 决定：agent 自己生成一对密钥。私钥只存在 agent 上；公钥经客户端交给 VPS 登记。VPS 只存公钥，不存任何能冒充 agent 的秘密。
- 启用 VPS 的步骤：用户在客户端为某台服务器启用 VPS并填入 VPS 地址 → 客户端经 SSH 让 agent 生成密钥对（若尚无）→ agent 返回公钥 → 客户端把公钥登记到 VPS → agent 用私钥登录 VPS。
- 直连令牌与登记密钥是两个东西，互不相通。登记密钥泄露，只能在 VPS 上假冒该 agent 登记，拿不到直连令牌；VPS 被攻破，拿不到任何能直连的凭据。

### Q6. 服务的启停与授权（已决定：D-25 至 D-28）
- 服务开关经直连完成，每次变更写审计日志。客户端只能切换 agent 已内置的服务，不能让 agent 启用未内置的服务。
- `service_actions` 保留，作为 systemd 启停的白名单，修改方式与服务开关相同。
- 服务开关不是安全边界：持有直连令牌的人本来就能取得 root 权限（D-25）。

### Q7. 插件（服务模块）的形态（已决定：D-29）
- 内核与插件的划分只为开发方便。服务随 agent 一起编译，随客户端一起分发。
- 不做独立的插件分发通道，VPS 不分发任何服务模块。
- 不做运行时加载外部插件。若将来要支持第三方插件，需另开决定，重新设计签名、沙箱和权限。
- 待定（未讨论）：内核与服务之间的接口，即服务如何注册、如何被开关、如何上报能力。D-29 只定了打包与加载方式，没有定这一层。

### Q8. 旧版本的迁移
- 建议：现有用户（已经通过 VPS 连接的服务器）需要一条迁移路径：客户端检测到旧 agent，提示用户通过 SSH 重装，或保留旧模式。
- 待定：是否保留旧的 VPS 自动分发模式作为过渡，以及保留多久。

### Q9. 现有 relay 的改动范围（已决定：更新分发移出 VPS）
- 决定：VPS 只保留两项职责：登记（用 Q5 的公钥验证在线 agent）、打洞会合（转交候选地址和随机数，不含任何令牌）。可选的代理出口与凭据无关，单独保留。
- 更新分发不再放在 VPS 上。改为：客户端为核心，客户端安装包内含 agent；连接服务器后，客户端自动把匹配的 agent 推送过去。新版本由作者手动发布到 GitHub Release。
- 移除：直连令牌的分发，以及客户端查询时拿到的任何凭据字段。
- 待定：移除后，现有的 agent 是否还能用。这涉及协议版本，要有兼容期。

## 6. 暂不涉及

- 多服务器的统一管理界面（属于界面设计，等入口稳定后再讨论）。

## 8. 发布密钥（v3）

v3 的发布密钥与 v2 完全隔离。

| 项目 | 值 |
|---|---|
| 算法 | ed25519 |
| 公钥（base64） | `ZkXgb9QfuaRzm77NoOxMTOrB+8hMkbx2lc5gRTKdtrk=` |
| key_id（公钥 SHA-256 前 16 位） | `87828dfb18459372` |
| 私钥位置 | `<release-key>`，仅当前用户可读 |
