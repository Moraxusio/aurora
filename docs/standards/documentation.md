# 文档规范

> 类型：文档规范 | 状态：生效 | 维护：项目维护者 | 更新：2026-11-16
> 适用：全部自有文档；第三方原文和已归档证据除外

## 单一入口与目录

`docs/README.md` 负责导航，仓库 `README.md` 只保留项目定位、当前交付和开发入口。

| 目录 | 回答的问题 | 更新方式 |
|---|---|---|
| `guides/` | 用户怎样完成任务 | 随行为修改 |
| `architecture/` | 模块如何协作、状态归谁 | 随设计修改 |
| `development/` | 开发者如何实现、检查和构建 | 随工作流修改 |
| `reference/` | 精确配置、协议能力和限制 | 与代码常量／能力上报核对 |
| `standards/` | 文档与协作规则 | 明确生效范围 |
| `decisions/` | 为什么做持久性的架构选择 | 编号记录，替代时保留旧决定 |
| `releases/` | 某版本增加什么、如何验收 | 一版本一文件 |
| `validation/` | 哪份源码在什么环境实测了什么 | 一次验收一记录 |
| `performance/` | 原始结果、日志、截图、源码指纹 | 保留原始证据及索引 |
| `archive/` | 旧规范、旧计划和历史讨论 | 加归档标记，只作追溯 |
| `templates/` | 新文档起点 | 维护模板，不填真实验收结果 |

禁止在 `docs/` 根目录新增专题文件，根目录只保留索引。禁止再维护同时包含计划、设计、所有版本变更和验收日志的长文件。

## 文件与元信息

1. UTF-8、LF、Markdown；文件名使用小写 `kebab-case.md`，索引 `README.md` 例外。
2. 验收文件使用 `YYYY-MM-DD-topic.md`；决定使用 `NNNN-topic.md`；版本说明以版本或候选名命名。
3. 每个当前文档只有一个一级标题，紧接以下两行；维护者写角色，不写个人私密信息。

```markdown
> 类型：使用指南 | 状态：生效 | 维护：客户端维护者 | 更新：2026-11-16
> 适用：3.22.0 Windows 客户端
```

状态只使用 **生效、候选、已记录、模板、已替代**。历史档案使用“已归档”提示和返回当前入口的链接。验收记录不使用“生效”冒充长期规范。

4. 当前文档必须从文档入口直接列出；历史文件由归档索引管理，证据由所在目录索引管理。
5. 使用相对 Markdown 链接指向其它文档。源码位置、配置键与命令用代码格式，避免把不可访问的机器绝对路径作为通用开发前提。

## 内容规则

- 指南按“前提 → 操作 → 预期结果 → 失败处理／限制”组织，给可执行命令及工作目录。
- 配置示例使用合成路径、令牌和模型名。解释命令在客户端、本地 agent 或远程 agent 的哪一端执行。
- 当前行为写在指南／参考；阶段测试数字写在验收记录；未来能力只写成待办，不能与已实现内容混用。
- 资源上限说明单位和统计范围，例如事务前后版本合计，不能把磁盘体积说成 RSS。
- 证据写清源码 HEAD **及是否有未提交修改**、工具链、运行参数、通过／失败／跳过数、未验项目。Profile、Release、协议夹具、真实账号各自只证明实际覆盖范围。
- 性能记录保留阈值、场景、样本量、分位数和异常帧；保留失败原始结果，修复后另记复验。不得只保留最好一轮。
- 私钥、授权码、用户配置、真实凭据、完整聊天正文不进入文档或分发包。

## 修改与归档流程

1. 先确定文档所属目录及现有权威页面，优先更新现有页面。
2. 修改功能时同步更新指南、配置与兼容边界；新增重大决定使用 ADR 模板。
3. 新文档加入入口；移动文件更新所有链接、源码注释、脚本复制路径和打包说明。
4. 过时规范迁入 `archive/<日期>/`，保留原文及历史编号，标记替代入口；不让旧版本说明继续承担当前规范。
5. 原始日志、JSON、源码哈希不重写成“新结果”。目录索引与迁移链接可以修正，记录仍归属原运行。
6. 运行 `powershell -NoProfile -File tools/check-docs.ps1`。全项目检查与完整打包会调用同一入口。

自动检查负责文件位置、命名、元信息、标题、索引覆盖、失效本地链接和旧入口引用；内容准确性仍由实现与实测证据支撑。
